Ask Yourself First: Where Do Your Passwords Really Live? ☘️🔐

No big decision today. Just a good question over a warm coffee, and a few reasons to take it seriously.

Wojciech Mruk · Friday Morning Coffee Insights #09

Start with you

Before we talk about clients, servers and tools, here is a story from home. My mother-in-law says she simply cannot remember passwords. “How would I know?” she asks. So she picks something she can remember: the dog’s name and the year she was born. Perfectly understandable. Also perfectly guessable.

The fix is not a better memory. The fix is not needing one. Take two minutes and be honest with yourself:

If you answered yes a few times, you are in good company. Almost everyone does, and that is exactly the point.

5 keys people use to build passwords (and why they are weak)

  1. Dates and names: Rex2015. Birthdays, kids and pets are on social media, and attackers try them first.
  2. Letter-to-digit swaps: P4ssw0rd. Cracking tools know every swap, so it adds almost nothing.
  3. Base word + counter: Client000 → Client011. Once one leaks, the next is a guess.
  4. Keyboard walks: qwerty, 1qaz2wsx. They feel random but follow the shape of the keyboard.
  5. Reuse with a tweak: same core everywhere, new last letter. One breached site opens the rest.

The map nobody drew

Ask around the office where the access to a client’s server lives. You will hear: Notepad++, an Excel sheet, a PDF someone got in 2022, that email from Tuesday. And my favourite: the password that ends in 000 on one system, 011 on another, and on a third one is something completely different, because someone “had to change it quickly”.

It is not an alarm yet. But it is a good moment to act, before it becomes one. At DairyGold we already run a Password Vault for the client. Maybe it is time to build the same thing for ourselves. First the cats over the fence, as they say, then the farm.

The idea: one cabinet, not a bigger key ring

A shared password manager gives every credential one encrypted home. Items sit in collections (for example, one per client and environment), people belong to groups (by job), and each group gets the permission it needs on each collection. A new colleague joins a group. A leaver is removed in one place. If a password changes, you change it once and everybody sees the current one.

Why this deserves a real look

  • Others already do it. Managed-service teams and security guidance such as NIST SP 800-63B treat password managers as normal, expected tooling.
  • We can run it ourselves. Vaultwarden, a Bitwarden-compatible server, already runs at one of our clients. Hosting it on our own servers is a realistic option, with the honest footnote that updates, HTTPS and tested backups would then be ours to own.
  • Changes become simple. Passwords stop flying around in emails, files and chats. When someone leaves or a secret may be exposed, rotating it is one edit in one place, not a hunt through inboxes. (Current guidance favours changing passwords on leavers and suspicion, not on a fixed calendar.)
  • It protects the private side too. The habit that saves a client login also saves your mailbox and your bank.

The Azure/AWS distinction is worth repeating because the names sound wonderfully universal. Yes, both can store a password. A whisky barrel can also store office paper, but that does not make it a filing cabinet. These services shine when an application retrieves a database password or API key through an identity and an API, not when an engineer needs a clear, shared client-access record.

House rules for the key cabinet

The safest product can still be deployed like a sieve. Before we migrate a single production password, we need a short set of non-negotiable rules:

  1. Individual vault accounts and strong MFA. Prefer phishing-resistant methods where practical. No shared “team” login to the manager itself.
  2. Least privilege by default. Start with no access, then grant the required client and role. Separate everyday support from highly privileged credentials.
  3. Two owners for administration and recovery. One is a bus factor; two is a beginning. Break-glass access must be protected, documented and tested.
  4. No uncontrolled exports. An exported CSV or JSON vault is a readable incident waiting for a filename. Restrict exports, protect any approved recovery copy, and delete migration files securely after verification.
  5. Patch and monitor. Keep server and clients current; watch availability and administrative events. Review logs with their limitations in mind rather than treating them as a magical security camera.
  6. Back up and rehearse recovery. Include the database and attachments, encrypt backups, separate them from the production host, and perform an actual restore test.
  7. Rotate on suspicion and after exposure. Moving a leaked password into a vault does not make it un-leaked. Change it first. Also review shared credentials when someone with broad access leaves.
  8. Review access regularly. A short quarterly review of groups, admin rights, stale accounts and old client entries is enough to prevent archaeological access.

For higher-risk administration, a password manager may be only one layer. Privileged access management, session approval, just-in-time access and individual admin accounts can provide stronger accountability than a shared administrator password. We should use the right level of control for the risk rather than making every login equally difficult.

One source of truth, zero password pub quizzes

I am not proposing we switch tomorrow. I am proposing we analyse it properly: we have the technical means, the example is already running, and the cost of doing nothing is a spreadsheet called Passwords_FINAL_v7.xlsx. The full story, with a rollout plan, is in Post 09.

Our version is a managed vault. One current record per credential. Collections that match clients. Groups that match responsibilities. Access information that includes N-able, Radmin, RDP, IP addresses and jumpboxes without scattering the details across email. And either a professionally operated cloud service or an in-house installation that we are genuinely prepared to maintain.

The goal is not to make access mysterious. It is to make it boring: authorised people get the current information quickly, everyone else does not, and nobody has to ask whether Final_FINAL2 is newer than Final_REAL.

Security is not remembering every password. It is knowing which door each one opens, who may use it, and when to take it back.
